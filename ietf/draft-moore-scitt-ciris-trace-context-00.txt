         Prompt Context Provenance for AI Agent Decision Traces
                draft-moore-scitt-ciris-trace-context-00

Abstract

   An AI agent that acts on a person's behalf makes each decision
   through several calls to language models: one stage drafts an action,
   others evaluate it, and others may veto it.  What each call was given
   decides what it can judge.  A record of the action alone cannot show
   whether a judging stage lacked a rule the drafting stage had, whether
   untrusted text reached a stage designed never to see it, or whether a
   stage was prompted in a language other than the one the person used.

   This document specifies a per-call context manifest.  It describes
   every contiguous piece of text placed into a model call (a segment)
   by what it is, where it came from, how far it can be trusted, which
   authority stands behind it, how long it lives, and which language it
   is in.  It specifies a closed-vocabulary context policy that says
   which stage may and must receive which kinds of segment, ablation
   stubs that stand in for text withheld from a stage, and the checks a
   verifier runs against the manifest and against the bytes actually
   sent.  It states the safety properties of the policy as invariants
   checked by a model checker.  The manifest is carried as the payload
   of a CEG trace row or of any SCITT signed statement.

1.  Introduction

   Several Internet-Drafts record what an AI agent did: the tool it
   called, the authorization it held, the decision it reached, and a
   digest of the model input (Section 11).  They answer "what was done,
   by whom, under whose authority".  They do not answer a question that
   comes before it: what was each model call actually given, and was it
   supposed to be given that?

   The question matters because an agent's decision is not one model
   call.  In the agent this document was developed against, a decision
   passes through up to fourteen call sites in four roles: a drafter
   that proposes an action, second passes that fill in a chosen verb,
   evaluators that score the situation, and judges (consciences) that
   may veto the draft (Section 2).  Some judges are deliberately denied
   the untrusted text the drafter saw, so that a persuasive request
   cannot argue a judge out of its veto.  This is input ablation.

   Measurement of that agent, before the mechanism in this document
   existed, found failures that no action record could show
   (Appendix A):

   *  A rule a Wise Authority (the agent's human overseer) had stated
      reached the drafter, but almost never the two ablated judges.  The
      judges then vetoed compliant replies as "invented policy".



Moore                      Expires 23 May 2027                  [Page 3]

Internet-Draft          Agent Context Provenance           November 2026


   *  The reason for a veto never reached the stage asked to revise the
      draft (0 of 162 retries).

   *  Raw user text reached the ablated judges inside a system-built
      record of earlier actions, in about a third of first-pass calls.
      The ablation leaked.

   *  A user's self-chosen display name was laid out where a verified
      identity belonged.

   All four were found by pattern-matching 42,998 prompts after the
   fact.  This document makes the same facts a signed record of every
   call.

1.1.  What This Document Adds

   Five properties distinguish this profile from the agent trace drafts
   surveyed in Section 11.  As far as the author has found, none of them
   is specified elsewhere for agent traces.

   1.  *Provenance of each piece of context.* Each segment carries its
       kind, provenance, source, trust level and lifecycle, and the
       authentication, authorization and accounting records that make it
       binding (Section 3).  Trust propagates: a segment is no more
       trusted than any segment whose bytes it contains.

   2.  *Withholding with a record.* A stage may be given a stub in place
       of a segment: closed-vocabulary properties of the withheld text,
       never its bytes (Section 5).  The manifest records what was
       withheld and a digest of it, and a verifier checks that the
       withheld bytes do not appear elsewhere in the call.

   3.  *Language as evidence.* Each segment records the locale its bytes
       were rendered in and how that is known, and the manifest lists
       the segments that fell back to another language (Section 3.7).

   4.  *Machine-checked policy.* The context policy is compiled from a
       closed vocabulary.  The same source generates the runtime guard
       and a TLA+ [TLA] specification whose invariants a model checker
       verifies (Section 9).

   5.  *Declared against observed.* Each segment records its span and a
       digest of its bytes in the message actually sent, so a verifier
       can check that the manifest describes the call and not an
       intention (Section 8).

1.2.  Scope

   This document specifies the manifest, the policy vocabulary, the
   stub, and the checks.  It does not specify how an agent decides, what
   any stage concludes, or how a tool call is authorized: the manifest
   records what models were given, not whether they were right.  It
   defines no new signature, receipt or transparency mechanism: those
   are [I-D.moore-scitt-ciris-ceg] and [RFC9943].

1.3.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Call:  One request to a language model.

   Stage:  A named call site in the agent's decision procedure.  Every
      call belongs to exactly one stage.

   Stage role:  What a stage does: drafter, second_pass, evaluator or
      judge (Section 2).

   Ablated stage:  A stage that by policy receives no untrusted text.

   Segment:  One contiguous run of text placed into a call, described as
      in Section 3.

   Assembler:  The component that builds a call's messages from
      segments, enforces the policy, and emits the manifest.  An
      implementation conforming to this document has exactly one
      assembler path for every call.

   Policy:  The table that says, for each stage and each kind of
      segment, whether the stage must, may or must not receive it, and
      in which form (Section 4).

   Manifest:  The per-call record specified in Section 6.

   Stub:  The closed-vocabulary description sent in place of a withheld
      segment (Section 5).

   Wise Authority (WA):  A human party whose signed grants make rules
      binding on the agent.  The term is that of [CC]; any deployment's
      equivalent overseer fills the same role here.

2.  The Decision Model

   A decision is the work an agent does on one thought: a unit of
   reasoning within a task.  The stages of the model are:

         +=============+========================================+
         | Role        | Stages in the reference implementation |
         +=============+========================================+
         | drafter     | aspdma (action selection)              |
         +-------------+----------------------------------------+
         | second_pass | tsaspdma, dsaspdma, fsaspdma,          |
         |             | msaspdma, rsaspdma (one per verb:      |
         |             | tool, defer, forget, memorize, recall) |
         +-------------+----------------------------------------+
         | evaluator   | csdma (common sense), dsdma (domain),  |
         |             | pdma (principles), idma (intuition)    |
         +-------------+----------------------------------------+
         | judge       | coherence, epistemic, entropy, optveto |
         |             | (optimization veto)                    |
         +-------------+----------------------------------------+

                     Table 1: Stages and their roles

   Evaluators run first and their results reach the drafter.  The
   drafter proposes an action; a second pass completes it for its verb.
   Every judge then reviews the draft.  A veto sends the thought back to
   the drafter with typed feedback (a retry), up to a depth limit.  A
   draft that survives review is executed.

   A deployment MAY name different stages.  This profile requires only
   that each stage has a stable name, one role, and an entry in the
   policy, and that the set of ablated stages is declared in the policy.

   In the reference implementation the ablated stages are entropy and
   optveto.  They judge the draft against the agent's own commitments
   and against signed rules, but never see the request that prompted it.

3.  Segment Taxonomy

   A segment is described on six independent axes.  The kind says what
   the text is; provenance, source, trust and lifecycle say where it
   came from and what it is worth; locale says what language it is in.
   Keeping the axes separate is deliberate: the earlier measurement
   mixed them, and the mixing is how leaks hid.

3.2.  Provenance

   Provenance applies to rule segments only, and is REQUIRED on them.

    +=================+==================================+===========+
    | Provenance      | Meaning                          | Trust     |
    +=================+==================================+===========+
    | user_chat       | stated by a user in conversation | untrusted |

    |                 | conversation, unsigned           |           |

    | signed_guidance | from a resolved deferral whose   | verified  |

    +-----------------+----------------------------------+-----------+
    | amendment       | from a landed, signed identity   | verified  |
    |                 | amendment                        |           |
    +-----------------+----------------------------------+-----------+

   A rule stated in conversation is advisory, whoever states it.  It
   remains part of the request or history segment it was said in.  In
   the reference policy no stage lists rule.user_chat or rule.wa_chat,
   so no such segment is ever produced; the values exist so that a
   policy that admitted one would be expressible and checkable.

3.3.  Source

   Which component produced the bytes: user_input, adapter_metadata,
   auth_context, signed_row, agent_profile, engine, llm_output,
   tool_output or provider_lib.  A kind MAY be restricted by the policy
   to one source.

3.4.  Trust

   Trust has three ordered levels: untrusted < verified < system.




Moore                      Expires 23 May 2027                  [Page 8]

Internet-Draft          Agent Context Provenance           November 2026


   *  untrusted: user-controlled or model-generated text.

   *  verified: established by the system against a credential or a
      signature.

   *  system: produced by the agent from its own state.

   The policy assigns each kind (and each rule provenance) a trust
   level.  A producer MAY state a lower trust for a segment than the
   policy's; it MUST NOT state a higher one.

   *Taint rule.* A segment's trust after taint is the minimum of its own
   trust and the trust after taint of every segment listed in its
   derived_from.  The manifest records trust after taint.  An
   action_record that quotes a user's words is therefore untrusted,
   whichever component built it.  A segment whose trust after taint is
   below the trust the policy requires for its kind is a tainted
   violation (Section 7).

3.5.  Lifecycle

   How long a segment lives: standing, per-task, per-message, per-
   thought, retry-only or per-call.  A per-task or per-thought segment
   records the task or thought it belongs to; one placed in a call for
   another task or thought is a cross_scope violation.

3.6.  AAA Carriers

   Each segment MAY carry three records.  The policy states which are
   REQUIRED for which kind.

   Authentication (authn):  The verified subject: subject identifier,
      role, and the verifier that established them.  REQUIRED on
      sender_identity.

   Authorization (authz):  The grant that makes the segment binding: its
      kind (amendment, deferral or response_attestation), its
      identifier, the authorizer, whether its signature verified, and
      when it was granted.  REQUIRED on amendment, on rule with
      provenance signed_guidance or amendment, and on wa_guidance.

   Accounting (acct):  The record tying the segment to the audit trail:
      audit entry, the hash of the signed row its bytes came from, the
      trace, and for conscience_feedback the veto and discharge
      identifiers.

   A judge that is asked whether a rule binds reads the rule's authz
   carrier, attested by the system, not prose claiming authority.

3.7.  Locale

   Each segment records locale, a language tag [RFC5646], and
   locale_basis:

   declared:  The producer stated the locale it actually served, after
      any fallback.  For text read from a localized prompt file, this is
      the file read, not the file requested.

   assembler_rendered:  The assembler rendered the bytes itself (for
      example, a sender line from its carrier in the call's language, or
      a stub line).

   unstated:  No component vouches for a locale.  User text, model
      output, and text authored in an agent's configuration are unstated
      unless their producer states otherwise.

   Two tags have fixed meanings here: mul for text that is deliberately
   multilingual (a polyglot prompt), and zxx for closed-vocabulary
   tokens with no linguistic content (a stub line).

   The call records language, the locale it was rendered for.  A segment
   is a locale fallback when its basis is declared, its locale is
   neither mul nor zxx, and its primary language subtag differs from
   that of the call's language.  The manifest lists every fallback
   segment in locale_fallbacks.  A regional variant (pt-BR in a pt call)
   is not a fallback.

   A segment joined from fields served in different locales (for
   example, a localized paragraph followed by one that fell back to
   English) records the locale that differs from the call's language, so
   that the segment is listed as a fallback.  A per-field fallback is a
   fallback: a producer that serves one field of a localized prompt from
   another language MUST record that field's segment with the language
   actually served.

   The reason this is evidence and not configuration: a judge prompted
   partly in English while the person wrote in Amharic is a different
   judge.  In the reference implementation this was first found by
   counting script characters in sent prompts; with this record it is a
   field of every call.

4.  The Context Policy

   The policy is a single document.  It has five parts:

   version:  An integer.




Moore                      Expires 23 May 2027                 [Page 10]

Internet-Draft          Agent Context Provenance           November 2026


   ablated_stages:  The stages that receive no untrusted text.

   kinds:  For each kind: its trust (absent for rule, whose trust comes
      from provenance), its lifecycle, which carriers are REQUIRED,
      whether it is rendered with a label, whether it is an accepted
      residual (Section 4.4), and the one source it may have, if fixed.

   rule_provenance:  The trust of each rule provenance.

   stages:  For each stage, an ordered list of rows.  A row is a kind
      (or rule.<provenance>), a predicate, and a form.  Row order is the
      stage's rendering order.

   stub_fields:  The closed set of fields a stub may carry (Section 5).

4.1.  Predicates

   A row's predicate says when the stage receives the kind.  The
   predicates are a closed set, each evaluated against facts the system
   establishes from its own state (signed rows, the authentication
   context), never from the segments being checked:

      +==========================+==================================+
      | Predicate                | Holds when                       |
      +==========================+==================================+
      | always                   | always                           |
      +--------------------------+----------------------------------+
      | never                    | never                            |
      +--------------------------+----------------------------------+
      | retry                    | the call is a retry after a veto |
      +--------------------------+----------------------------------+
      | signed_guidance_in_force | signed WA guidance from a        |
      |                          | resolved deferral applies        |
      +--------------------------+----------------------------------+
      | amendment_in_force       | a landed identity amendment      |
      |                          | carries a rule that applies      |
      +--------------------------+----------------------------------+
      | trusted_rule_in_force    | either of the two above          |
      +--------------------------+----------------------------------+
      | id_scoped                | the rule in force is scoped to a |
      |                          | verified identity                |
      +--------------------------+----------------------------------+
      | advisory_rule            | an unsigned rule was stated in   |
      |                          | conversation                     |
      +--------------------------+----------------------------------+

   When a predicate holds, the kind is REQUIRED at that stage; a call
   without it is a missing_required violation.  When it does not hold,
   or the kind has no row, the kind is forbidden.  Facts MUST NOT be
   derived from the segments, or a missing rule could hide itself.

4.2.  Form

   A row's form is full (the segment's bytes are sent) or stub (a stub
   is sent in place of the bytes).  A stub row is permitted only at an
   ablated stage, and only for an untrusted kind.

4.3.  Static Checks

   A policy is admissible only if a compiler confirms all of the
   following before it is deployed.  The reference compiler refuses a
   policy that fails any of them.

   1.  *Closed vocabulary.* Every kind, provenance, source, trust,
       lifecycle, predicate, form and stub field is one this document
       names.

   2.  *Firewall.* At an ablated stage, every untrusted kind is either
       absent, a stub row, or a declared residual.

   3.  *Signed rules only.* No stage requires a rule whose provenance is
       untrusted.

   4.  *No laundering.* A kind the policy marks system is admitted only
       with an empty derived_from at runtime; the assembler enforces
       this per call.

   5.  *Identity layout.* Any stage that admits display_name admits it
       only as a labelled kind, never inside sender_identity.

   6.  *Evidence sufficiency.* Wherever a trusted rule can be in force,
       every judge receives that rule with its authorization carrier.

   7.  *Coverage.* Every declared kind is used by some stage, and every
       stage is assigned a role.

   The same policy source generates the runtime guard, the TLA+ contract
   (Section 9) and the conformance tests, so that code, model and
   behaviour cannot silently diverge.

4.4.  Residuals

   Some untrusted text cannot be withheld from a judge without defeating
   the judge.  The draft under review is the main case: it may quote the
   request.  A policy names such kinds as residuals.  A residual is sent
   in full at an ablated stage, is excluded from the leak check
   (Section 8), and is recorded as untrusted.  Residuals are a stated
   limit of the ablation, not an exception to it.

   kind of thing it was, without its bytes.  Without a stub the stage

6.  The Context Manifest

6.1.  Encoding

   The manifest is a CBOR map [RFC8949] with text-string keys, encoded
   deterministically (Section 4.2 of [RFC8949]) when it is the payload
   of a signed statement.  Following [I-D.moore-scitt-ciris-ceg], it
   contains no floating-point values: every number is an integer.
   Digests are SHA-256 [RFC6234].

   The reference implementation emits the same structure as JSON on its
   reasoning stream, with digests as lowercase hexadecimal text.  A
   producer that signs a manifest converts each digest to a byte string
   of 32 octets (6 octets for a stub digest), omits each optional member
   the JSON form gives as null, and otherwise keeps the structure.

6.3.  Field Semantics

   call_id  Unique per call.  When the producer has none, it is the
      first 32 hexadecimal digits of SHA-256 over the stage, task,
      thought, retry index and messages digest joined by |.

   retry_index  0 on the first pass, n on the n-th retry after a veto.

   policy_sha256  SHA-256 of the policy document's bytes.  A verifier
      MUST hold the policy with this digest to run the checks of
      Section 8.

   guard_mode  fail_closed means a violation aborts the call (used in
      testing and QA).  strip_and_incident means the offending segment
      is removed, an incident is recorded, and the call proceeds (used
      in production).  A manifest with violations in fail_closed mode
      never accompanies a sent call.

   segments  In rendering order.  message_index and [span_start,
      span_end) locate the segment in the content of the message sent,
      in Unicode scalar values.  sha256 is over the UTF-8 encoding of
      exactly that span.  For a stub segment, the span holds the stub
      line, stub holds the stub, and withheld_sha256 is over the UTF-8
      encoding of the withheld bytes.

   messages_sha256, messages_digest_form  A digest of the messages as
      sent.  Form ciris-json-1 is the form the reference
      implementation's model bus hashes: a JSON array of the message
      objects in order, each with role and content, members in insertion
      order, separators ", " and ": ", non-ASCII characters unescaped,
      encoded as UTF-8.  Form jcs is the JSON Canonicalization Scheme
      [RFC8785] over the same array.  Absent means ciris-json-1.  New
      implementations SHOULD use jcs and state it.

   sent_messages_match  Set by the component that sent the call: true
      when the messages it sent hash to messages_sha256.  Absent when
      the manifest was not finalized at the sending component.



Moore                      Expires 23 May 2027                 [Page 18]

Internet-Draft          Agent Context Provenance           November 2026


   provider_capture  Whether text a provider library added to the call
      (for example, an output schema appended to the last message) was
      reproduced and recorded as schema_instruction segments.
      unrecognized_change means the library rewrote the messages in a
      way the producer could not record; a verifier treats such a call's
      segment list as incomplete.

   The untrusted_bytes check normalizes text by collapsing whitespace

8.  Verifying a Manifest

   A verifier holds the manifest, the policy whose digest the manifest
   names, and, where available, the messages as sent.  It runs these
   checks and reports each as passed, failed, or not run with the
   reason.

   V1 Policy conformance:  Recompute, from the segment records and the
      facts the verifier can establish, every violation of Section 7
      except untrusted_bytes.  Report any the manifest does not list.

   V2 Sent bytes:  With the messages as sent: recompute messages_sha256,
      and for each segment the digest of its span.  Report any mismatch.
      This is the check that catches a call that bypassed the assembler,
      or a manifest that misdescribes its call.

   V3 Taint:  Recompute trust after taint from derived_from and the
      policy.  Report any segment recorded at a higher trust.

   V4 Ablation:  At each ablated stage, confirm every untrusted, non-
      residual segment has form stub; with the messages as sent and the
      withheld bytes, run the untrusted_bytes search over the text
      outside residual spans.

   V5 Carriers:  Confirm each required carrier is present, and that
      every authz with signature_verified true resolves to a grant whose
      signature the verifier can check.

   V6 Locale:  Recompute locale_fallbacks from the segment records and
      language.  A deployment that requires a locale MAY additionally
      require that no segment of kind stage_instruction or
      pipeline_position is a fallback.

   V7 Completeness:  Report provider_capture values unsupported_mode,
      unrecognized_change and unavailable: the segment list may not
      cover the call.

   A verifier that lacks the messages as sent can run V1, V3, V5, V6 and
   V7.  V2 and V4 require the bytes.  This separation lets a manifest be
   published while the prompts, which may hold personal data, are not
   (Section 14).

9.  Formal Model

   The policy's safety properties are stated as invariants of a TLA+
   specification and checked with the TLC model checker.  The
   specification, H3EREContextFlow.tla, models one thought through
   drafting, judging, retry and execution across six scenarios (no rule;
   a user's own preference; an unsigned WA rule; signed WA guidance; a
   signed amendment; an identity-scoped amendment with an impersonation
   attempt) and a bounded retry depth.  Its context inputs are
   generated: the contract configuration from the policy by the compiler
   of Section 4 (ContractPolicy.tla), and the measured configuration
   from manifests and sent prompts of real runs (ContextData.tla).

10.  Carrying the Manifest

10.1.  As a CEG Trace Row

   In [I-D.moore-scitt-ciris-ceg], an agent's own reasoning trace is a
   row of the family trace:{form}:{version}.  A context manifest is
   carried in such a row as follows:

   *  The row is signed only by the agent's own key.  [CC]
      (Section 3.1.5) assigns the trace family's attest and withdraw
      uses to the agent signer kind; a node, host or person key MUST NOT
      sign it.  The machine-checkable form is the key-role contract of
      [CC] (manifests/key_roles.json, family trace:{form}:{version},
      signer kind agent).

   *  The row names its run: run_kind is in the signed bytes, from the
      closed set of [CC] (production, prod-personal, prod-managed, qa,
      battery, mock).  A mock trace is refused at federation-tier
      admission outright, with refusal token trace_run_kind_mock: a mock
      model's output attests nothing about any agent.  A node MAY hold
      its own mock rows locally (for QA and tests).

   *  The manifests of a thought's calls are members of the trace
      payload, in call order.  The payload is deterministically encoded
      CBOR with no floating-point values.  Any score or confidence
      elsewhere in the trace is a fixed6 integer, as
      [I-D.moore-scitt-ciris-ceg] requires.

   *  The policy document a manifest names by policy_sha256 SHOULD
      itself be published as a signed row, so that a verifier can obtain
      it.

   The signed object, its signature, its names and references, and its
   admission are those of [I-D.moore-scitt-ciris-ceg]; this document
   repeats none of them.





Moore                      Expires 23 May 2027                 [Page 23]

Internet-Draft          Agent Context Provenance           November 2026


10.2.  As a SCITT Signed Statement

   A manifest MAY be the payload of any SCITT signed statement [RFC9943]
   (a COSE_Sign1 [RFC9052] message registered with a transparency
   service).  The checks of Section 8 are unchanged.  Two guarantees of
   a CEG row are lost:

   *  *The family's door.* A CEG node admits a trace row only if its
      family's static checks pass, including the closed run_kind.  A
      generic transparency service admits a statement without inspecting
      its payload, so a mock or malformed manifest can be registered.

   *  *The key-role check.* A CEG node refuses a trace row signed by any
      key but the agent's own.  Outside CEG, nothing binds the signer of
      a manifest to the agent whose calls it describes; a verifier MUST
      establish that binding by other means before relying on it.

11.  Relationship to Other Work

   Several individual Internet-Drafts record agent actions in SCITT-
   style statements.  Measured against the five properties of the
   Introduction:

   *  [I-D.thaha-scitt-agent-execution-evidence] digests the request and
      response octets at each model call, which this document's
      messages_sha256 and span digests also provide.  It records digests
      of the system prompt and skills, but not who supplied each piece
      of context or at what trust, and its digest is taken before any
      content is withheld; it has no notion of a stage denied some
      context.

   *  [I-D.durga-wimse-ctx-isolation] attests a taint level for a
      context window per tool call, and refuses a call rather than
      withholding content.  This document's taint rule is per segment
      and its stubs record withholding.

   *  [I-D.sharif-agent-audit-trail],
      [I-D.emirdag-scitt-ai-agent-execution],
      [I-D.mih-scitt-agent-action-capsule] and
      [I-D.gilda-audit-agent-audit-record] record actions, decisions,
      delegation and input hashes, and some redact the stored record.
      Redacting a record after the fact is different from withholding
      text from a model before the call, which is what a stub records.

   *  [I-D.birkholz-vcon-ai-agent-extension] attributes each message of
      an agent conversation to a party.





Moore                      Expires 23 May 2027                 [Page 24]

Internet-Draft          Agent Context Provenance           November 2026


   *  The OpenTelemetry GenAI conventions [OTEL-GENAI] define spans for
      model calls and can capture input messages, but carry no
      provenance, trust or signature.

   *  [I-D.kuehlewind-audit-architecture] describes an architecture for
      auditing agent delegation and interactions across domains, and
      [I-D.cosme-audit-agent-traceability] the attestation and registry

      [I-D.birkholz-verifiable-agent-conversations] specifies verifiable

      parties; this document addresses what each model call inside one

   None of these, as far as the author has found, records the locale of
   model input or states its properties as model-checked invariants.
   This document is complementary to all of them: an action record can
   reference the manifests of the calls behind the action.

13.  Security Considerations

   *What the manifest proves.* A manifest signed by the agent's key is
   the agent's own account of its calls.  Check V2 against independently
   captured bytes (for example, at a model gateway the agent does not
   control) is what turns that account into evidence.  Without it, a
   compromised agent can emit a consistent but false manifest.







Moore                      Expires 23 May 2027                 [Page 27]

Internet-Draft          Agent Context Provenance           November 2026


   *Ablation is a stated limit, not a guarantee.* Residuals are
   untrusted text sent to ablated stages by design.  The leak check is a
   substring search over normalized text: paraphrase, translation or
   encoding defeats it.  It detects copying, not influence.

   *Stubs leak properties.* A stub reveals the kind, size bucket, author
   role and disposition of withheld text, and its quote share reveals
   how much of it the draft repeats.  The field set is closed so that
   what leaks is known.

   *Facts versus segments.* Policy predicates are evaluated against
   facts from trusted state.  An implementation that derived them from
   the segments could let a missing rule hide itself, or let a forged
   segment make itself required.

   *Provider libraries.* A library that rewrites messages after the
   assembler can add text the policy never admitted.  The
   provider_capture field makes that visible; it cannot prevent it.

14.  Privacy Considerations

   A manifest contains identifiers, digests and closed-vocabulary
   values, never segment text; violation details never contain segment
   text.  It does contain subject identifiers in authn carriers, which
   are personal data where the subject is a person.

   Digests of short, guessable text can be inverted by trying
   candidates. withheld_sha256 and the stub digest of a short request (a
   size of short is at most 200 characters) are open to this.  A
   deployment that publishes manifests SHOULD replace these with keyed
   digests whose key is held with the prompts, or omit them, and record
   which it did; the reference implementation uses unkeyed SHA-256 and
   is affected.

   Publishing manifests while withholding prompts is the intended use:
   V1, V3, V5, V6 and V7 run on the manifest alone.
