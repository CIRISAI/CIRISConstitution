                Signed Reasoning Traces of CIRIS Agents
                    draft-moore-scitt-ciris-trace-00

Abstract

   An AI agent that acts on a person's behalf reaches each action
   through a sequence of steps: it gathers context, runs several
   evaluations, selects an action, submits the selection to checks that
   can veto it, and then acts.  Most of those steps are calls to
   language models.

   This document specifies the CIRIS reasoning trace: one signed record
   per unit of agent work (a thought), sealed when the action is taken.
   The trace lists every step and every model call in the order the
   recording component received them, with scores, outcomes, sizes,
   costs and durations, and, at higher disclosure levels, reasoning text
   and the prompts and completions themselves.  It specifies three
   disclosure levels, the exact bytes the agent's Ed25519 signature
   covers, how a trace is carried as a row of the CIRIS Epistemic
   Grammar (CEG), when a trace exists at all, and the checks a consumer
   runs before relying on one.  It records where the published
   specification and the shipping implementation disagree.

1.  Introduction

   A record of what an AI agent did is more useful when a party other
   than the agent and its operator can check it.  Several Internet-
   Drafts record the action, the authority behind it, and digests of
   model inputs (Section 12).  This document specifies a record of the
   steps in between: how the agent arrived at the action.

   The record is the trace of the CIRIS agent [CIRISAGENT].  The agent
   is a made thing, held in stewardship by its operator; the trace is
   its own account of one unit of work, which the agent calls a thought.
   A thought passes through a fixed pipeline (Section 4): the thought
   starts; context is gathered; three evaluators score the situation; an
   identity check measures how independent the agent's sources were; an



Moore                      Expires 23 May 2027                  [Page 3]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   action is selected; a verb-specific second pass may refine it;
   conscience checks may veto it and send it back for reselection; and
   the action is taken.  Every language-model call made along the way is
   recorded as its own event, linked to the step that issued it.

   A third party can check a trace for three reasons.  First, the trace
   is the payload of a CEG statement signed by the agent's own key
   (Section 8), so any change after signing is detectable, including the
   disclosure level and the link from each model call to the step that
   made it.  Second, the identifier of the agent in every trace is
   derived from that key (Section 3.1), so a verifier can bind the trace
   to the key without trusting a directory's label.  Third, the trace is
   carried as a signed row of the CIRIS Epistemic Grammar
   [I-D.moore-scitt-ciris-ceg], whose admission rules refuse a trace
   signed by any key but the agent's, a trace whose fields break its
   pinned schema, and, at federation-tier admission, a trace from a run
   on a mock model (Section 9).

   A trace is the agent's own account.  The signature proves who gave
   the account and that it is unchanged, not that it is true.  Checking
   it against records made by parties the agent does not control is
   outside this document; [I-D.moore-scitt-ciris-trace-context]
   describes one such check for model calls.

   This document is one of three:

   *  [I-D.moore-scitt-ciris-ceg] specifies the signed row, its
      encoding, its names and references, and admission.  This document
      repeats none of them.

   *  This document specifies the trace: the trace:complete:v1 payload.

   *  [I-D.moore-scitt-ciris-trace-context] specifies the per-call
      context manifest, carried as a member of this document's LLM_CALL
      event (Section 5.10).

1.2.  Scope

   In scope: the CompleteTrace object, its components and event shapes,
   the disclosure levels, the signed bytes, carriage as a CEG row, the
   lifecycle rule that decides when a trace exists, and validation by a
   consumer.

   batch envelope and its correlation metadata), how a collector stores
   them, and how scores are aggregated across traces.

3.1.  The Agent Identifier

   agent_id_hash is the first 16 hexadecimal characters, lowercase, of
   the SHA-256 [RFC6234] digest of the raw public key bytes of the
   agent's Ed25519 signing key:

   agent_id_hash = lowercase_hex(SHA-256(public_key))[0..16]

   An emitter MUST derive it exactly so, from the key that signs the
   trace.  The same value appears on the envelope and on every
   component, and the two MUST be equal.

   Because the derivation is from the signing key, a consumer that holds
   the public key can recompute the identifier and check it
   (Section 11).  The identifier is pseudonymous, not anonymous: any
   party holding the public key can compute it.  It is 64 bits long;
   Section 15 discusses collisions.

   Releases of the reference implementation before v2.23.0 fall back to
   hashing the agent's name, or to the literal unknown, when the signing
   engine is unavailable (test environments).  A trace carrying such a
   value fails the check above and MUST NOT be admitted at federation
   tier (Appendix A).  From v2.23.0 a component with no signing engine
   is refused, not captured.

3.2.  The Trace Identifier

   trace_id identifies the trace within the agent's traces.  It is
   unique per agent by convention only; consumers MUST key on the pair
   (agent_id_hash, trace_id), never on trace_id alone, because an agent
   controls its own trace_id values.

   trace_id is assigned by the substrate when it seals the trace, and
   the implementation's traces carry the thought identifier itself
   (Appendix B).  Earlier versions of the wire contract and JSON Schema
   gave the format trace-<thought_id>-<YYYYMMDDHHMMSS>.  A consumer MUST
   NOT parse trace_id (Appendix A).

3.3.  The Deployment Profile

   deployment_profile carries six labels the operator declares about the
   deployment.  They are inside the signed bytes, so an intermediary
   cannot relabel a trace.

   agent_role:  A free-form lowercase role name.

   agent_template:  The identifier of the agent template.




Moore                      Expires 23 May 2027                  [Page 9]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   deployment_domain:  Exactly one value from the closed set in the CDDL
      above.  general is the value for multi-domain assistants.

   deployment_type:  An operator-declared label.  Not a closed set in
      practice: operator values (for example personal, business,
      research, nonprofit), the original lifecycle values (development,
      test, staging, production, research, decommissioned) and the run
      kind markers mock, qa and battery all occur in it.  A consumer
      MUST NOT treat it as an enumeration.  The run kind belongs in its
      own member (Section 9.2).

   deployment_region:  An ISO 3166-1 alpha-2 country code, global, or
      null for "not disclosed".  The member is present even when null.

   deployment_trust_mode:  sovereign (no federation participation),
      limited_trust (partial), or federated_peer (full).  This is the
      agent's declared intent, not a finding about it.

   An agent with no operator configuration emits the defaults
   deployment_domain = "general", deployment_type = "production",
   deployment_trust_mode = "sovereign", deployment_region = null,
   agent_role = the lowercased agent name, and agent_template = <agent
   name>-default-unspecified.  These are well-formed and a consumer MUST
   accept them.

3.4.  Schema Versions

   The shape of a trace at each trace level is fixed by the agent's per-
   level field schema, the pinned artifact trace_format_v{n}.json ([CC],
   Section 3.1.5; Section 7).  This document does not fix a value of
   trace_schema_version.

   Today the emitter stamps trace_schema_version 3.0.0, and the verifier
   of the current signature form selects its canonicalizer by that
   string (Section 8.2).  The version survives the move to statement
   signatures: the storage engine's release 62.0 accepts 3.1.0, which
   names the context_manifest member, and the server's release 0.6
   stamps it.  The trace format remains named by the row family's leaf
   trace:complete:v1; an additive member needs no new leaf.  Neither
   release had shipped at the time of writing (Section 13).

   Each component is one event of the pipeline:

   agent_id_hash:  Equal to the envelope's (Section 3.1).

   component_type:  The pipeline stage, fixed by event_type (table

    +-------------------------+------------------+-------------------+

    | (deprecated)            |                  |                   |
    +-------------------------+------------------+-------------------+
    | VERB_SECOND_PASS_RESULT | verb_second_pass | at most once      |
    +-------------------------+------------------+-------------------+
    | CONSCIENCE_RESULT       | conscience       | once per check    |
    |                         |                  | pass              |
    +-------------------------+------------------+-------------------+

   The mapping is fixed.  A consumer MUST reject a component whose
   component_type does not match its event_type, and MUST reject an
   event_type outside the set defined for the trace's schema version:
   silent acceptance of an unknown type would let a new payload pass
   without review.

   The pipeline order of the steps is:




Moore                      Expires 23 May 2027                 [Page 11]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   1.  THOUGHT_START.

   2.  SNAPSHOT_AND_CONTEXT.

   3.  DMA_RESULTS: three evaluators run in parallel.

   4.  IDMA_RESULT.

   5.  ASPDMA_RESULT: an action is selected.

   6.  VERB_SECOND_PASS_RESULT, when the selected verb has a second
       pass.

   7.  CONSCIENCE_RESULT.  If a check overrides the selection, the
       pipeline returns to step 5 with is_recursive true; steps 5 to 7
       repeat until the selection passes or an override action is taken.

   8.  ACTION_RESULT.

   LLM_CALL events occur throughout, each naming the step that issued it
   (Section 5.10).

   The components array is in the order the emitter received the events,
   which is not the pipeline order and not timestamp order: in the
   example of Appendix B, a model call issued for action selection
   precedes the DMA_RESULTS component, and timestamps are not monotonic.
   A consumer MUST NOT infer a causal link from array position.  The
   causal links are attempt_index (Section 6) and the parent link of
   each LLM_CALL.  The array order is nonetheless inside the signed
   bytes and MUST be preserved.

4.1.  Empty Values

   Before signing, the emitter removes from data, recursively, every
   member whose value is null, the empty string, the empty array or the
   empty object.  The values 0 and false are kept.  A consumer MUST read
   an absent member as "not emitted at this level or for this event",
   never as null.

   Whether a container left empty by this removal is itself removed is
   not stated by the sources (Section 13).

5.10.  LLM_CALL

   One call to a language model provider, successful or not.  Every call
   the pipeline makes is recorded, including retries.

   parent_event_type and parent_attempt_index name the pipeline event
   that issued the call; together with the trace's (agent_id_hash,
   trace_id, thought_id) they identify that event uniquely.  Because
   they are in the signed bytes, nobody can move a call to a different
   parent without breaking the signature.  An emitter MUST carry both
   whenever the issuing step is known.

   status is one of ok, timeout, rate_limited, model_not_available,
   instructor_retry or other_error. error_class names the exception on
   failure.  attempt_count counts re-prompts after an unparseable
   response (1 is the first try); retry_count counts provider-level
   retries (0 is the first attempt).

   prompt_hash is the SHA-256 of the messages sent, as lowercase hex.
   It is the messages_sha256 of [I-D.moore-scitt-ciris-trace-context].

   An LLM_CALL component MAY carry a member context_manifest at trace
   level detailed and above: the per-call context manifest specified by
   [I-D.moore-scitt-ciris-trace-context], which describes each piece of
   text placed into the call by kind, provenance, trust, lifetime and
   language.  The verified sender's subject_id in the manifest depends
   on the level:

   *  At detailed it is HMAC-SHA256 [RFC2104] of the identifier string
      under a per-agent secret that the agent holds and never discloses,
      truncated to 16 hexadecimal characters, with subject_id_form
      hmac_sha256_16.  Where the secret is unavailable the identifier is
      omitted, never sent as it is.

      subject_id_form raw.

   *  At generic the context_manifest member is omitted.

   The keyed form is used because user identifiers are low-entropy: an
   unkeyed digest could be reversed by trying candidates, and would link
   one person across every agent that saw them.  The keyed value is
   stable within one agent and cannot be linked across agents.

   a trace carrying it is admitted under the current 3.0.0.  It is
   emitted from CIRISAgent v2.23.0; no trace carrying it is published

   storage engine's release 62.0 and stamped by the server's release
   0.6, neither shipped at the time of writing (Section 13).

6.  attempt_index

   Every component carries attempt_index inside data.  It is a counter
   per (thought_id, event_type), starting at 0 and increasing by one
   with each event of that type in receipt order.  For the types that
   occur once per thought it is always 0.  For ASPDMA_RESULT,
   CONSCIENCE_RESULT and LLM_CALL it orders the repetitions.

   It exists because timestamps of concurrent events can be equal.  A
   consumer that stores components MUST key them on

   (agent_id_hash, trace_id, thought_id, event_type,
    attempt_index, timestamp)

   and MUST NOT drop timestamp from the key: it guards against a
   counting defect collapsing two events into one.  It MUST NOT drop
   agent_id_hash, which prevents one agent from claiming a key that
   another agent's trace will need.

   trace re-signed at another level has another signature, and a
   consumer cannot be misled about which profile it holds.

   The default level is generic.  The implementation lowers a configured
   full_traces to detailed when the substrate cannot scrub personal data
   from text.

   The per-level field schema, which says which members each level
   carries, their types, and their string and list bounds, is the
   agent's artifact.  [CC] (Section 3.1.5) requires that it be pinned by
   hash in the Constitution's evidence pins and vendored by tag by every
   substrate that admits traces, so that emitter and admitter derive
   from one artifact.  The bounds of the implementation's egress schema
   [EGRESS-SCHEMA] are part of its contract: tokens at most 64
   characters, identifiers and labels at most 128, URLs at most 256,
   reasons at most 500, the attestation summary at most 1024, free text
   at most 65536, lists at most 32 items, maps at most 64, and opaque
   JSON at most depth 8, 256 items and 8192 characters per string.

   A trace that violates the pinned schema MUST be refused, never
   truncated, with the refusal token trace_field_shape_violation ([CC],
   Section 3.1.5): a truncated row is a silently altered signed record.



Moore                      Expires 23 May 2027                 [Page 24]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   The rule binds the admitter.  The implementation's emitter filters
   each component before signing instead: it drops a member the level
   does not allow or whose type does not fit, truncates over-long text
   and cuts over-long lists, and logs and counts each violation without
   its value.  Because this happens before signing, the signed trace is
   what the agent attests to.  Before v2.23.0 the alteration is silent
   in the signed bytes.

   From v2.23.0 the emitter records each alteration in the component's
   signed data, as egress_alterations: a list of at most 64 marks, with
   a count of any beyond that.  A mark gives the member's path, the kind
   of alteration (truncated, dropped_wrong_type or
   dropped_not_in_schema), and the original_length; a truncated mark
   also gives sha256, the SHA-256 digest of the original value.  A
   dropped value gets no digest: it was content in the wrong place, and
   a digest of a short value can be confirmed by guessing.  A member
   above the trace level is not an alteration and is not marked.  The
   emitter discards any egress_alterations a producer supplies before
   filtering, so the marks are the filter's own.  With the marks, an
   emitter's cut is declared in what the agent signs rather than silent;
   the admitter's rule is unchanged.  Whether the Constitution's text
   should say so, and how the emitter's and admitter's schemas are bound
   by one pinned hash, are open (Appendix A).

   egress-alteration = {
     path: tstr,
     kind: "truncated" / "dropped_wrong_type" / "dropped_not_in_schema",
     original_length: uint,
     ? sha256: tstr,                  ; truncated only
   }

8.  Signatures

8.1.  The Normative Signature

   The signature of a trace is the signature of the CEG statement that
   carries it (Section 9).  The signed object, its composite signature,
   its keys and its admission are those of [I-D.moore-scitt-ciris-ceg];
   this document repeats none of them.  The signer is the agent: [CC]
   (Section 3.1.5) and its key-role contract (manifests/key_roles.json,
   family trace:{form}:{version}, signer kind agent) give a trace's
   attestation and its withdrawal to the agent alone, and an admitter
   verifies the statement at the door.  A node, host or person key MUST
   NOT sign a trace.







Moore                      Expires 23 May 2027                 [Page 25]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   Because the statement signature covers the whole payload, it covers
   everything the current form covers (Section 8.2): the trace level,
   the deployment profile, every component and its attempt_index, and
   every parent link of a model call.

   No released implementation yet emits a trace as such a statement.
   The transition is in Section 13.

8.2.  The Current Form: Per-Trace Ed25519

   What ships today is a separate Ed25519 signature carried inside the
   trace, over canonical bytes of the trace.  It is described so that
   traces signed this way can be verified.  It is being replaced by the
   statement signature above: the storage engine's version 62 (the
   server's 0.6 release, not shipped at the time of writing) removes the
   earlier-form trace verification and verifies traces as agent-signed
   statements.  An implementer SHOULD NOT build a new emitter or
   verifier on this form alone.

8.2.1.  What Is Signed

   With trace_schema_version 3.0.0, the signed bytes are the JCS
   canonicalization [RFC8785] of the following JSON object, built from
   the trace:

   {

   Exactly these members are present, and no others: an unknown member
   of the envelope or of a component is not signed, and a verifier MUST
   NOT add it to the canonical object.  strip_empty is the removal of
   Section 4.1.  attempt_index is inside data and therefore signed.

   The signature is pure Ed25519 [RFC8032] over the signed bytes, with
   the agent's signing key.  signature is its 64 bytes in base64 with
   padding ([RFC4648], Section 4).

8.2.2.  Canonical Shapes by Version

   The verifier of this form selects the canonical shape and the
   canonicalizer from trace_schema_version, which is itself inside the
   signed bytes:

     +=========+====================+================+===============+
     | Version | Envelope members   | Component      | Canonicalizer |
     |         | signed             | members signed |               |
     +=========+====================+================+===============+
     | 2.7.0   | 9, no              | 4, no          | legacy        |
     |         | deployment_profile | agent_id_hash  |               |
     +---------+--------------------+----------------+---------------+
     | 2.7.9   | 10                 | 5              | legacy        |
     +---------+--------------------+----------------+---------------+
     | 3.0.0   | 10                 | 5              | JCS [RFC8785] |
     +---------+--------------------+----------------+---------------+

               Table 4: Canonical shapes of the current form

   The legacy canonicalizer is Python's json.dumps(obj, sort_keys=True,
   separators=(",", ":")) with its default ASCII escaping.  It agrees
   with JCS on traces whose text is all ASCII and differs on any other
   text.

   A verifier MUST select the shape and canonicalizer from
   trace_schema_version alone, and MUST NOT try another shape when
   verification fails under the selected one.  A verifier MUST reject a
   version it does not support.  At 2.7.0 a verifier MUST ignore any
   deployment_profile on the envelope and any agent_id_hash on a
   component; neither is signed at that version.

8.2.3.  Keys

   The key of this form is the agent's own signing key, the same key
   that signs the agent's audit entries.






Moore                      Expires 23 May 2027                 [Page 27]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   signature_key_id names the key for lookup.  How a consumer obtains
   the public key for a signature_key_id is not specified by the current
   sources: the registration path of the wire contract has been retired
   in the implementation (Section 13).  Whatever the lookup, the
   consumer checks the key against agent_id_hash (Section 11).

8.2.4.  Verification

   A verifier of this form:

   1.  obtains the public key named by signature_key_id;

   2.  checks that agent_id_hash equals the first 16 lowercase
       hexadecimal characters of SHA-256 of that key;

   3.  selects the shape and canonicalizer from trace_schema_version,
       rejecting an unsupported version;

   4.  builds the canonical object from the received trace and
       canonicalizes it;

   5.  verifies the Ed25519 signature over those bytes; and

   6.  rejects the trace on any failure.

   A consumer MUST verify before it stores a trace as a record.

9.  Carriage as a CEG Row

9.1.  The trace:complete:v1 Row

   A trace is carried as a CEG row [I-D.moore-scitt-ciris-ceg] of the
   family trace:{form}:{version}; the canonical leaf is
   trace:complete:v1, which carries the trace after scrubbing.  The
   signed object, its composite signature, its names, references,
   receipts and admission are those of [I-D.moore-scitt-ciris-ceg].  The
   statement's signature is the trace's signature (Section 8).

   [CC] (Section 3.1.5) states these rules for the row:

   1.  *Identifiers.* The envelope carries a non-empty trace_id and a
       non-empty agent_id_hash, equal to those of the trace.









Moore                      Expires 23 May 2027                 [Page 28]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   2.  *Exactly one body.* The envelope carries exactly one of an inline
       trace (the CompleteTrace), within the 1 MiB payload bound of [CC]
       (Section 2.6.1.6), or a manifest object of schema
       trace_manifest:v1 naming it (Section 9.3).  This trace manifest
       is not the per-call context manifest of
       [I-D.moore-scitt-ciris-trace-context].

   3.  *Shape and provenance.* Admission validates that the row parses,
       and nothing more: an admitted trace:* row is guaranteed
       parseable, and that is all admission claims.  Provenance rides
       the producer's signature, verified at promotion to federation
       tier ([CC], Section 5.3.2.6) and again by consumers.  Neither
       substitutes for the other.

   4.  *Field schema.* The per-level field schema is the agent's
       artifact, trace_format_v{n}.json, pinned by hash in the
       Constitution's evidence pins and vendored by tag by every
       substrate that admits traces.  A row that violates it is refused,
       never truncated, with trace_field_shape_violation (Section 7).

   5.  *Run kind.* The trace carries run_kind in the signed bytes
       (Section 9.2).  A mock row is refused at federation-tier
       admission only, with trace_run_kind_mock; the three production
       values are admitted alike.

   6.  *Signer and withdrawal.* The family is reserved ([CC],
       Section 3.4.5).  Its attestation and its withdrawal are the
       agent's own, signer kind agent; an admitter MUST refuse a trace:*
       row signed by any other key.

   7.  *Erasure.* Only the signer's withdrawal, or after retirement the
       custodian its retirement row names, erases a trace.  An owner MAY
       stop its own node holding a trace's bytes; that reaches no copy
       another party holds under a consent grant.

















Moore                      Expires 23 May 2027                 [Page 29]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   trace-row-payload = {
     dimension: "trace:complete:v1",
     trace_id: tstr,                  ; non-empty
     agent_id_hash: tstr,             ; non-empty
     run_kind: run-kind,              ; CC 3.1.5; see {{run-kind}}
     ( trace: { * tstr => any }       ; a CompleteTrace
     // manifest: trace-manifest )
     * tstr => any,                   ; members every CEG row carries
   }

   run-kind = "production" / "prod-personal" / "prod-managed"
     / "qa" / "battery" / "mock"

   trace-manifest = {
     schema: "trace_manifest:v1",
     content_hash: tstr,              ; "sha256:" then lowercase hex
     byte_len: uint,                  ; positive

   }

9.2.  The Run Kind

   Every trace row names the kind of run that produced it, in the signed
   bytes, from the closed set production, prod-personal, prod-managed,
   qa, battery and mock ([CC], Section 3.1.5). prod-personal and prod-
   managed mark a production run on a personal install or a managed
   deployment; production remains valid for an emitter that does not
   distinguish them, and admission treats the three alike.  qa marks a
   test-harness run and battery an evaluation battery, both of which may
   use a real model.  mock marks a run on a mock model.

   A federation-tier admitter MUST refuse a mock row with
   trace_run_kind_mock: a mock model's output attests nothing about any
   agent.  The refusal is at federation tier only: a node MAY hold its
   own mock rows locally, for tests.

   *Implementation.* Before v2.23.0 the implementation carries the run
   kind inside deployment_profile.deployment_type, which is signed, as
   one of mock, qa or battery overriding the operator's value, with no
   marker for a production run and no prod-personal or prod-managed.  It
   keeps mock traces out of its federation store at the source.

   From v2.23.0 every component's signed data also carries run_kind from
   the six-value set.  A test-harness or mock setting wins; otherwise an
   operator's CIRIS_DEPLOYMENT_KIND of managed or personal; otherwise
   prod-managed under the agent's deployment manager and prod-personal
   elsewhere.  deployment_type is unchanged.  The value is in the signed
   bytes but in each component, not as a member of the envelope or of



Moore                      Expires 23 May 2027                 [Page 30]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   the CEG row.  The trace format 3.1.0 schema [TRACE-SCHEMA-JSON]
   requires it in every event's data.  An admitter reads it from the
   components, in this order (the rule is to be stated in Section 3.1.5
   of [CC] after its v1.0-rc21 release):

   1.  If any component carries mock, the trace is refused with
       trace_run_kind_mock.

   2.  Otherwise every component MUST carry the same run_kind value.  A
       trace any of whose components differ, or of which any component
       lacks run_kind, is refused with trace_field_shape_violation.
       This check compares values exactly: a trace mixing prod-personal
       and production is refused.  The three production values are
       treated alike only at admission, after this check passes.

   The value can change within a trace for one reason: the agent's mock
   model can engage partway through a thought, so that earlier
   components carry a production or qa value and later ones mock.  An
   emitter MUST NOT relabel a component's run_kind to match an earlier
   component's: doing so would carry mock output under a production
   label.  The disagreement reaches the admitter, which refuses the
   trace.  Whether the value also becomes an envelope or row member is
   open (Appendix A).

9.3.  The Oversize Form

   A CEG payload is bounded at 1 MiB of deterministic encoding
   ([I-D.moore-scitt-ciris-ceg]).  When a trace is larger, the row
   carries manifest instead of trace.  trace_manifest:v1 is a payload
   schema tag, not a family:

   schema:  The literal trace_manifest:v1.

   content_hash:  sha256: followed by the lowercase hexadecimal SHA-256
      of the trace's canonical bytes.

   byte_len:  The length of those bytes, a positive integer.

   component_count:  The number of components in the trace.

   The trace's bytes travel on the blob plane of [CC] and are named by
   hash in the row's evidence_refs.









Moore                      Expires 23 May 2027                 [Page 31]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


9.4.  trace_summary

   trace_summary:{kind} is a post-scrub digest of a trace for
   consumption on another node, used when the trace itself is out of
   scope or over the size bound.  The same self-emission rule applies,
   and a summary carries no claim the full trace does not.  Its payload
   is not specified by the sources (Section 13).

9.5.  Numbers in the Row

   A CEG payload carries no floating-point value: a score is an integer
   at the fixed scale of 10^6, and any other non-integral number is a
   CBOR decimal fraction (tag 4 of [RFC8949])
   [I-D.moore-scitt-ciris-ceg].  A trace is JSON, and many of its
   members are non-integral numbers: every score in [0, 1]
   (entropy_score, plausibility_score), k_eff, cost_usd, cost_cents and
   duration_ms among them.  The trace's own scores are not fixed6
   integers.

   The sources do not say how these map into a CBOR statement
   (Section 13).  Under the statement signature the signed bytes are the
   CBOR payload, so the mapping is free of the JSON canonicalization;
   but a conversion that rounds (to fixed6, for example) changes the
   values the agent attests to, so the mapping must be applied by the
   agent before it signs, never by a relay.  While a current-form
   signature is also carried, a verifier must be able to reconstruct the
   JCS bytes of the JSON trace exactly, which a lossy conversion
   prevents.  The implementation's carrier is the earlier JSON row form,
   which carries the trace's numbers as JSON numbers (Section 14).

10.  The Action Anchor and Orphan Purge

   A trace exists only when its thought produces an action.  The emitter
   seals and signs the trace when ACTION_RESULT arrives; a thought that
   times out, ends without acting, or is abandoned produces no trace.
   This is the anchor rule of [CC] (Section 1.13.6), which Section 5.3.2
   applies to the durable trace: a trace is durable only when it is
   anchored on the record of an act.  Reasoning that produced no act is
   working state, not history.

   [CC] states the rule as duties:

   *  Every execution path that produces an external effect (every
      utterance, every tool call, every emission through an adapter)
      MUST close with a terminal result row.  In this document's terms
      that is the ACTION_RESULT that seals the trace.





Moore                      Expires 23 May 2027                 [Page 32]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   *  An in-flight trace that reaches no terminal event MUST be purged
      after a declared, bounded age, and the emitter MUST export a count
      of the traces it purges, so that an auditor can see how much is
      discarded while its contents stay unavailable.

   *  The purge cannot erase evidence of a consequential act.  If it
      ever did, the defect is in the action path, not the purge.

   The implementation purges orphan traces after a configured age
   (default the larger of 120 seconds and twice the sweep interval) and
   logs the number purged by each sweep.  Whether that count is exported
   as a metric, as [CC] requires, is not determinable from the agent's
   sources.  That every effect-producing path closes with a terminal
   event is not yet tested; [CC] requires that it be represented as a
   named wager wherever the control is claimed, and this document so
   represents it.

   A consumer that needs records of interrupted reasoning will not find
   them in traces.  [CC] allows an operator to enable a bounded,
   privacy-scoped plane for incomplete receipts as an explicit opt-in;
   this document does not specify one.

11.  Validation by a Consumer

   A consumer that relies on a trace, whether it admits it, stores it or
   scores it, MUST:

   1.   Verify the trace's signature (Section 8), including the check of
        agent_id_hash against the key.

   2.   Check that every component's agent_id_hash equals the envelope's
        (at 2.7.9 and later).

   3.   Check every event_type against the set of its schema version and
        every component_type against the mapping (Section 4), and reject
        the trace on a mismatch.

   4.   Check that the trace has exactly one ACTION_RESULT.

   5.   Check that, for each event_type, the attempt_index values are 0,
        1, 2 and onward in array order without gaps or repeats.

   6.   Check that each LLM_CALL carrying a parent link names an
        (event_type, attempt_index) present in the same trace.  A call
        whose parent is absent SHOULD be held but MUST NOT be linked.

   7.   Read absent members as not emitted (Section 4.1), and group by
        trace_level before concluding that reasoning data is missing.



Moore                      Expires 23 May 2027                 [Page 33]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   8.   Keep every repeated event: every ASPDMA_RESULT,
        CONSCIENCE_RESULT and LLM_CALL.

   9.   As a CEG admitter, apply the row rules of Section 9: the agent's
        key only, the closed run_kind with mock refused at federation
        tier, and the pinned field schema, refused not truncated.

   10.  Reject a trace whose schema version is newer than it supports,
        and say which version it supports.

   A consumer MAY reject a component whose agent_id_hash differs from
   the envelope's as malformed even where step 2 does not apply.

   Note to the RFC Editor: please remove this section before
   publication.

   *  *Run kind member.* [CC] requires a signed run_kind from a six-
      value set on the envelope.  CIRISAgent v2.23.0 carries the six

      also an envelope or row member, and the rule for a trace whose
      components disagree, are not agreed.

   *  *Refuse, not truncate.* The implementation's emitter truncates
      over-long values before signing; [CC] forbids truncation at
      admission.  CIRISAgent v2.23.0 declares each cut in the signed

15.  Security Considerations

   *An account, not a proof.* A valid signature shows that the agent's
   key signed the trace and that it has not changed since.  It does not
   show that the steps happened as recorded.  A compromised agent can
   sign a consistent but false trace.  Comparing a trace with records
   made by parties the agent does not control, such as a model gateway,
   is what turns the account into evidence.

   *Identifier collisions.* agent_id_hash is 64 bits.  A targeted
   collision against one agent's identifier costs about 2^64 SHA-256
   evaluations, and a collision between any two of a population about
   2^32.  The identifier is an index and an anti-collision prefix for
   stored components, not a security boundary: a consumer MUST verify
   the signature with the full key, and MUST NOT accept a trace on a
   matching agent_id_hash alone.

   *Agent-controlled identifiers.* trace_id and thought_id are chosen by
   the agent.  Keying stored components without agent_id_hash would let
   one agent pre-claim keys another agent's traces need.





Moore                      Expires 23 May 2027                 [Page 37]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   *Version confusion.* In the current form the version selects the
   canonicalizer and is itself signed.  Trying several shapes until one
   verifies would let an attacker choose the interpretation; Section 8.2
   forbids it.  At 2.7.0, members a later version signs are unsigned,
   and a verifier that read them would accept injected values.

   *Level confusion.* The level is signed, so a trace cannot be
   presented as having been produced under a different level.

   *Parent links.* The link from a model call to its step is signed.  A
   collector cannot reattribute a call's cost, latency or failure to
   another step without invalidating the trace.

   *Unknown events.* Accepting an unknown event_type would admit a
   payload no schema has reviewed.  Consumers reject it.

   *Mock runs.* A trace from a mock model looks like a real one.  The
   run kind is the only signed marker.  For traces from releases before
   v2.23.0 an admitter relies on deployment_type and on the emitter
   keeping mock traces local; from v2.23.0 it reads run_kind from the
   components.

   *Unspecified signatures.* The ML-DSA-65 members are not specified.
   Relying on them could give a false sense of post-quantum protection.

   *Truncation.* A filter that truncates before signing produces a valid
   signature over an altered record.  The signature then attests to the
   truncated text, and nothing in the trace says what was removed.

16.  Privacy Considerations

   A trace describes how an agent handled a person's request, so it can
   carry personal data ([RFC6973]).  The trace level decides how much.

   *generic.* No prompt, completion or reasoning text.  It does carry
   the agent's name, model and handler names, timings, token counts and
   costs, which can reveal activity patterns, and the agent-written
   attestation summary.  In the example of Appendix B, which predates
   the current egress schema, a generic trace carries the free-text
   dsdma_domain label "theology / philosophy of suffering", which
   describes the subject of the person's request, and the provider
   endpoint base_url.  The current schema moves both to detailed.

   *detailed.* Adds channel identifiers, key identifiers and
   fingerprints, provider endpoints, short reasons written by a model
   (which can paraphrase the request), and prompt digests.  A digest of
   a short or guessable prompt can be inverted by trying candidates.
   The context manifest at this level carries each verified sender as a



Moore                      Expires 23 May 2027                 [Page 38]

Internet-Draft         CIRIS Agent Reasoning Trace         November 2026


   keyed digest (HMAC-SHA256 under a per-agent secret the agent never
   discloses, truncated to 16 hexadecimal characters, subject_id_form
   hmac_sha256_16).  Without the secret it cannot be reversed by trying
   candidate identifiers, and it differs between agents, so it does not
   link one person across agents.  Within one agent it is stable and
   links that person's traces to one another.  The protection lasts only
   while the secret is kept: a party that learns it can try candidates
   as against an unkeyed digest.  At full_traces the identifier is
   carried raw.

   *full_traces.* Adds prompts and completions verbatim, conversation
   history and memories: the person's own words.  The implementation
   lowers this level to detailed where personal data cannot be scrubbed.

   *agent_id_hash.* Links every trace of one agent.  It identifies the
   agent's key, not a person, but an agent serving one person links that
   person's traces.

   *Erasure.* A person whose data is in a trace keeps the route of [CC]:
   withdrawing consent starts a deletion clock.  The trace itself is
   erased only by its signer or custodian (Section 9).

   Location and timezone metadata that the implementation sends beside
   traces, under consent, are outside the CompleteTrace and its
   signature and are not specified here.

Appendix A.  Divergences Between the Sources

   Each entry is a point where, at CIRISAgent commit 59b7e5d, the wire
   contract, the JSON Schema [TRACE-SCHEMA-JSON-270], the
   implementation, an emitted trace, or [CC] disagreed.  "Specified" and
   "Shipped" describe that commit.  This document follows the code where
   the question is what ships, and states the Constitution's rule where
   the question is what is required.

   Each entry's status is as of release v2.23.0-stable (commit 2b6a85c,
   merging pull request 1370).  The release adds a Section 0 ("As
   shipped") to the wire contract [FSD-TRACE], generates the JSON Schema
   [TRACE-SCHEMA-JSON] from the egress schema, and fixes entries in the
   code.

   Transport:  Specified: HTTP POST of batches to a collector, with key
      registration.  Shipped: HTTP shipping and registration retired;
      sealing, signing and storage moved to ciris-lens-core.  Status:
      contract corrected to the code in v2.23.0 (Section 0).

   Schema version:  Specified: 2.7.9 in the contract text, const 2.7.0
      in the JSON Schema.  Shipped: 3.0.0, JCS.  Status: contract
      corrected and JSON Schema regenerated from the code in v2.23.0.

   trace_id:  Specified: trace-<thought_id>-<YYYYMMDDHHMMSS>; schema
      pattern ^trace-.  Shipped: equals thought_id.  Status: contract
      corrected and JSON Schema regenerated from the code in v2.23.0.

   Envelope members:  Specified: 12 members.  Shipped: also pqc_key_id,
      pubkey_ml_dsa_65, signature_ml_dsa_65.  Status: contract corrected
      to the code in v2.23.0 (Section 0).

   agent_id_hash:  Specified: MUST be the key derivation.  Shipped:
      falls back to a hash of the agent name, or unknown, without a
      signing engine.  Status: fixed in v2.23.0: with no signing engine
      the component is refused and counted, never captured under a name
      hash or unknown.

   Event types:  Specified: 10, closed.  Shipped: 15 in the taxonomy
      (five credit and deferral types), capture of DEFERRAL_ROUTED off
      by default.  Status: contract corrected and JSON Schema
      regenerated from the code in v2.23.0.

   Components per trace:  Specified: at most 6 components and five
      component types in the JSON Schema.  Shipped: 16 components in the
      example; seven component types in the core pipeline, twelve with
      the credit and deferral types.  Status: contract corrected and
      JSON Schema regenerated from the code in v2.23.0.
