# The Wire (ciris_constitution-1.0-rc12-wire.pdf, 112 pages)

**Care score:** 3
**One-line verdict:** A battle-hardened, byte-exact protocol specification whose cryptographic and canonicalization surfaces are exceptionally clear, but which needs a targeted pass to resolve an E2E multicast contradiction, specify the inner onion-packet wire layout, and clean up a few rendering and house-rule glitches.

## Strengths
- **Explicit, non-overclaiming adversary model:** Section 1.13.3 bounds the meaning of "privacy" to content-holding confidentiality and cohort-scoped visibility, explicitly listing non-goals and mapping 14 distinct adversary classes against what is and is not addressed (pp. 2–4).
- **Closed determinism surface:** Section 2.6.1.1.1 pins the three determinism rules RFC 8785 (JCS) leaves open—set vs. sequence array ordering, lowercase hex vs. RFC 4648 §4 standard base64, and millisecond-precision `Z`-suffixed timestamps—closing cross-implementation signature divergence by construction (pp. 29–31).
- **Single-source signed-object tables:** Section 2.6.1.7 enumerates the exact placement (`signed:row`, `signed:envelope`, `signed:envelope-extra`, `beside`, `local`) and type of every member of the attestation row and key record, generated from the same data file as the CDDL and test vectors (pp. 36–61).
- **Inline byte-exact conformance vectors:** Canonical subject hashes with reject vectors (pp. 16–17) and deterministic CBOR `record_id` preimages (p. 102) give an independent implementer immediate, local verification targets.
- **Explicit contract vs. intake size bounds:** Section 2.6.1.3 cleanly separates the interop-visible 1 MiB JCS contract bound from the mandatory local unparsed-octet intake ceiling, preventing unbounded-buffering DoS vulnerabilities in compliant parsers (pp. 34–35).

## Weaknesses
- **Internal contradiction on multicast transport (pull-only vs. push):** Section 2.1 defines `delivery_mode: push` as "substrate fans out to the live-delivery set per CC 5.3.3.4" (p. 11), and Section 5.3.3.2 specifies "direct Reticulum Links between participants (low-latency push; no relay tree needed at small N)" (p. 87). Yet Section 5.3.3.5 Decision E2 states unconditionally: "E2 — pull-only: Multicast is pull-only... There is no relay or fan-out tree" while Decision E3 immediately below it defines `Fan-out` (p. 92).
- **Underspecified wire layout for the Anonymous Tier (onion routing):** Section 5.4.6 normatively specifies the 3-hop X-Wing onion routing tier ("Once a node runs the tier, it relays onion traffic for others by default", p. 111), but unlike `SealedAvChunk` (p. 89) or `symbol_envelope` (p. 103), it provides no byte layout, header size, KDF info label, AEAD algorithm, or routing-header offset table for an onion packet ("An onion packet is a layered packet of fixed length...", p. 111). A second implementer cannot build a conforming relay from this text.
- **Ambiguous canonicalization of `roles` on `SignedKeyRecord`:** In Section 2.6.1.7 (p. 60), `roles` has Placement `beside` and Array kind `set`, with the note: "Serialised as roles; the record also carries roles inside the signed registration_envelope." In Section 5.3.4 (p. 95), `GenesisBundle` is hashed via JCS (`bundle_fingerprint` is `sha256` over the JCS-canonical bundle), which includes `holders: ["<SignedKeyRecord>"]`. Because JCS does not sort arrays automatically, if `beside` members of `SignedKeyRecord` are included in the JCS preimage of `GenesisBundle`, `roles` must be explicitly required to be pre-sorted at emission, or `bundle_fingerprint` will diverge.
- **Historical/design-evolution residue in normative text:** Section 2.3.5 says "The baseline envelope encoded producer authority alone (`attesting_key_id`); `subject_key_ids` adds the missing half" (p. 13); Section 2.4.1.1 table row 4 says "(existing primitive, new admission path)" (p. 23); Section 2.1 `listed` says "and the new CC 5.3.3 streaming endpoint set" (p. 12).
- **Comparative claims naming external projects:** Section 1.13.3.1 compares stream key-updates to MLS ("the way MLS PCS provides", p. 2); Section 2.3.2.1 compares string construction across languages ("a Rust implementation cannot construct the string at all, while a Python implementation using `surrogatepass` emits WTF-8", p. 15); Section 2.6.6.3 compares H3 to "(S2, Geohash)" (p. 66); Section 5.3.2.6 remarks that "iOS has no WebM / Opus playback" (p. 84); Section 5.3.3.5 E1 references "interoperability with Python RNS" and "a standard LXMF client" (pp. 92–93).

## Opportunities
- **Harmonize E2/E3 in 5.3.3.5 with 5.3.3.2:** A two-sentence edit in 5.3.3.5 Decision E2 (p. 92) clarifying that *broadcast / large-group* multicast is pull-only while *small-group realtime* uses direct-link push per 5.3.3.2 eliminates the contradiction between E2 and E3/2.1.
- **Either pin the onion packet bytes or mark 5.4.6.3–6 as a staged slot:** Either add the byte-offset table, KDF label, and AEAD suite for the 3-hop X-Wing onion packet in 5.4.6 (p. 111), or explicitly state that the wire layout lives in a companion manifest / future minor version so implementers know why byte vectors are absent.
- **Fix the broken markdown link and table overflows:** A mechanical pass over the markdown source will fix the leaked link on p. 5 and the four clipped code/table lines on pp. 24, 32, and 71.

## Threats
- **Unimplementable mandatory relay requirement:** Section 5.4.6 states that "a serve node cannot opt out" of relaying Anonymous Tier onion traffic and is out of conformance (`seat_opted_out` / `seat_without_hop_key`) if it does not participate (p. 5, p. 111). Because the onion packet wire format and KDF labels are not specified in 5.4.6, no independent implementer can build a conforming serve node from this volume alone—directly contradicting Page 1's promise ("The specification an implementer builds a second, independent producer and consumer from").
- **Post-quantum vs. classical authenticity discrepancy on MLS Welcome:** Section 5.3.2.4.3.1 establishes a strict federation-wide invariant that every signature is hybrid Ed25519 + ML-DSA-65 ("no classical-only", p. 82). However, Section 5.4.4 ("Inviter signature", p. 106) specifies that the inviter signs the HPKE encapsulation bytes with **ML-DSA-65 alone** ("sign the encapsulation bytes with ML-DSA-65 over the following length-delimited encoding"). A hostile reviewer or cryptographer will ask why the hybrid defense-in-depth rule (protecting against a lattice break via Ed25519) was dropped on the MLS Welcome admission ceremony.
